# Сравнение BI-инструментов для демо-проекта pocketstack

## Контекст

Стек демо-проекта:

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────────┐     ┌──────────────┐
│   sources   │ ──▶ │  sqlmesh (pref)  │ ──▶ │  DuckDB         │ ──▶ │  cube.dev    │
│  (CSV/API)  │     │  или dbt         │     │  → ducklake     │     │  semantic    │
└─────────────┘     └──────────────────┘     │  (lakehouse)    │     │  layer       │
                                             └─────────────────┘     └──────┬───────┘
                                                                              │
                                                     Postgres-wire SQL API   │ GraphQL/REST
                                                     (port 15432)            │
                                                                              ▼
                                                                     ┌──────────────┐
                                                                     │  BI-инструмент│
                                                                     └──────────────┘
```

Требования к BI-инструменту:

1. Подключение к **cube.dev** как источнику (Postgres-wire SQL API / REST) — метрики определяются в Cube, BI только визуализирует
2. Возможность прямого чтения **DuckDB** (отладка, локальные эксперименты, обход Cube для raw-данных)
3. Прозрачный путь на **ducklake** (формат читается через DuckDB — инструмент не должен заметить миграцию)
4. Совместимость с **sqlmesh**: BI читает материализованные модели из DuckDB, специфичной интеграции не требуется
5. Лёгкость: git-native, статический деплой или один бинарь, без тяжёлой серверной части

## Разбор по инструментам

### Evidence — рекомендованный выбор

- **Нативный Cube-коннектор** (`type: cube` в `connection.yaml`): cubes и views видны как таблицы, метрики остаются едиными в Cube — ровно наша архитектура
- Нативный DuckDB: два источника в одном проекте (Cube для метрик, DuckDB для raw/отладки)
- Дашборды = markdown + SQL в git, деплой статики на любой хостинг, превью в CI
- Ограничения: визуализации из коробки скромные (но есть VegaPlot/ECharts), своя SvelteKit-тема; для сложных лейаутов придётся писать компоненты

```yaml
# connection.yaml — два источника демо-проекта
sources:
  cube:
    type: cube
    host: localhost
    port: 15432
    user: ${CUBESQL_USER}      # из .env (историческая заметка: нативного type: cube нет)
    password: ${CUBESQL_PASSWORD}
    database: cube
  duckdb_local:
    type: duckdb
    path: ../warehouse/pocketstack.duckdb
```

### Observable Framework — альтернатива для кастомного UI

- First-class DuckDB (датафлоу на Arrow, быстрые большие выборки)
- Cube подключается через Postgres-клиент (`pg` + `DatabaseClient`) — работает, но обвязка своя
- Выбор, если демо-проект перерастёт в продуктовый фронтенд на React/D3

### Rill — интерактивная разведка, не прод

- Построен на DuckDB — читает наш warehouse напрямую, мгновенный time-series-explore
- **Конфликт идеологий**: свой metrics-слой дублирует Cube; для демо семантики это минус
- Роль: локальный инструмент исследователя в дополнение к Evidence, не клиент Cube

### Quarto — не для этого проекта

- Документно-ориентированный (отчёты, PDF) — не интерактивный BI

### marimo — не для этого проекта

- Хорош для прототипов аналитики в Python, но это код приложений, а не дашборды на семантическом слое

### Lightdash — исключён

- Жёстко привязан к dbt-проекту; при предпочтении sqlmesh не применим

## Рекомендация

```
Демо-проект:  Evidence  ←  cube.dev (SQL API)  ←  DuckDB/ducklake  ←  sqlmesh
Разведка:     Rill (локально, в обход Cube)
Эволюция UI:  Observable Framework (если понадобятся кастомные React-компоненты)
```

## Риски и ограничения

- **Cube SQL API** — подмножество SQL (read-only, без оконных функций в некоторых версиях, LIMITATIONS в доке Cube); сложную логику оставляем в sqlmesh/Cube, BI только фильтрует и агрегирует
- **ducklake** — доступ через DuckDB-расширение: убедиться, что версия DuckDB в Evidence/Rill поддерживает extension; для демо можно начать с чистого DuckDB-файла
- **Evidence Cloud-фичи** (SSO, scheduled sources) платные — для демо достаточно OSS-core
