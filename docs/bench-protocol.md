# Протокол оценки запросов pocketstack

Версия: 1.0 (2026-10-25). Реализация: `packages/harness/harness/bench.py`, запуск `just bench`.

## 1. Назначение

Единый лог оценки golden-вопросов (12 шт., см. `harness/golden.py`):
- **корректность** — rows-паритет трёх путей (компактно, полный разбор — `just verify`);
- **производительность** — latency каждого пути, N итераций, p50/min.

Каждый прогон протоколируется в `results/` — история накапливается, не перезаписывается.

## 2. Три пути выполнения

| Путь | Что измеряем | Комментарий |
|---|---|---|
| **REST** | `POST /v1/load` с `renewQuery: true` | сквозной semantic layer; кэш Cube принудительно отключён — каждый прогон бьёт в DuckDB |
| **SQL API** | pg-wire `:15432`, SQL из golden | накладные расходы pg-wire + планировщик Cube |
| **REF** | эталонный SQL к DuckDB marts напрямую | базлайн самого движка (верхняя граница скорости) |

N = 3 итерации на путь. Метрики: **p50** (медиана) и **min** — мс, wall-clock.
Данные детерминированы (dbgen sf=1), так что сравнение прогонов между собой валидно.

## 3. Каталог results/ (лог, в git)

```
results/
├── index.md                    # журнал прогонов: run, commit, паритет, Σp50 по путям
├── queries/                    # файлы запросов — SQL от Cube (/v1/sql), по одному на вопрос
│   └── <id>.sql                #   детерминированы; смена содержимого = смена SQL-хэша
└── runs/<YYYY-MM-DDTHHMMSS>/   # один прогон `just bench`
    ├── detail.csv              # ДЕТАЛЬНО: question_id × path × iteration → ms, rows
    ├── summary.csv             # СВОДНО (машиночитаемо): id, rows, parity, p50/min, sql_hash
    └── summary.md              # СВОДНО (таблица для чтения, со ссылками на queries/<id>.sql)
```

## 4. Методика прогона

1. `just cube` — сервер с `CUBEJS_DUCKDB_QUERY_LOG` (ground truth доступен).
2. `just bench` — для каждого вопроса:
   - `POST /v1/sql` → SQL сохраняется в `results/queries/<id>.sql`, считается sha256-хэш;
   - N итераций каждого пути → `detail.csv`;
   - свежие строки каждого пути → rows-паритет (канонизация как в verify) → колонка `parity`;
   - p50/min → `summary.csv` / `summary.md`.
3. Строка дописывается в `results/index.md` (шапка создаётся при первом прогоне).
4. Exit code: 0 — все parity OK, 1 — есть FAIL, 2 — Cube недоступен.

## 5. Интерпретация (базовый ориентир, sf=1, 2026-10-25)

| Наблюдение | Объяснение |
|---|---|
| REST 6–10 мс | DuckDB быстр, Cube добавляет немного; renew исключает кэш |
| SQL API ~50 мс | фиксированные накладные pg-wire на roundtrip (min до 7–10 мс без очереди) |
| REF 3–40 мс | сам движок; count(DISTINCT ...) по 6M строк — дороже простой суммы |
| Хэш стабилен между прогонами | SQL генерится детерминированно (см. verify: детерминизм 12/12) |

Рост REF при неизменном REST → деградация DuckDB (файл/кэш/размер данных).
Рост REST при стабильном REF → деградация Cube (очередь, конфиг).
Смена SQL-хэша в `queries/` → изменилась генерация запросов (модель/версия Cube) —
обязательный разбор перед сравнением latency со старыми прогонами.

## 6. Правила ведения

- `results/` — в git: каждый прогон коммитится (или пачкой), это журнал проекта.
- Между прогонами не менять одновременно модель данных и версию стека — иначе сравнение
  latency теряет смысл (хэши/commit в шапке позволяют проверить).
- При росте sf (Stage 7) — те же вопросы, новый ряд в index.md; сравнение только внутри sf.
